# QQ 收藏接口与验收边界

检查版本：NapCat v4.18.38，日期 2026-10-21。

当前官方发布包的公开收藏动作 `fetch_custom_face` 与 `fetch_custom_face_detail` 都只接受 `count`，内部调用 `fetchFavEmojiList("", num, true, true)`。未发现可供应用使用的分页游标、权威收藏总数或容量查询契约。因此 UI 分页只分页展示已读取快照，下载也只保证处理快照内条目，不宣称完整备份或已测出账号容量。

`app/scripts/qq_diagnostics.py` 在显式提供 `QQ_DIAG_ENDPOINT`、`QQ_DIAG_ACCOUNT`、`QQ_DIAG_TOKEN` 后，进行两轮 count 48／2000／5000 只读比较。结果只记录数量、差集大小和稳定性，不输出账号、资源标识、图片 URL 或令牌。每次列表读取前后校验账号，HTTP 429 即停止。扩大 count 后数量稳定不构成全量证明。

批量上传、删除与下载共用串行任务。项目间间隔 0.5 秒且可取消；账号／收藏读取收到 HTTP 429 时最多重试两次，每次最多等待 5 秒。写请求不自动重传，未确认提交需先核对。模拟大批量与 429 回归验证的是客户端策略，不代表 QQ 真实限速阈值或账号配额。

普通 QQ 无重启附加尚未实现。官方 Framework 的公开加载入口接收 QQ 可执行路径、DLL 路径与脚本路径，用于启动并加载，没有经过确认的指定 PID 附加接口。已有 NapCat HTTP 服务可以手工连接，但这不等于向普通 QQ 进程附加；工具不会为此终止或接管外部 QQ。

当前验证区分如下：

- QQ 下载、账号隔离、哈希校验、取消和批量调度：模拟网络与隔离真实 SQLite 回归通过；本轮没有写真实 QQ 收藏。
- S3：使用真实 boto3／botocore 客户端和 Stubber 验证请求、签名配置与流式读取；真实 S3 尚需应用设置中的目标与凭据。
- WebDAV：模拟协议测试通过，未连接真实用户存储。
- NapCat：官方 Framework 原包真实下载并验证 release SHA-256，安装目录通过检查，未自动执行。
- DPI：实际主窗口与设置窗口在 144→96→144 DPI 间程序移动，DPR 与原生 DPI 一致，逻辑视口保持不变；手工拖动视觉认可待验收。
- Windows 包：已准备根 CI 和可选发布流程，本机缺必需工具链，未生成完整包或正式发布。
